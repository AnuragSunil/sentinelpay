# Weak spots

Known gaps, shortcuts and things I do not fully understand yet. Be honest: this is the to-do list for learning and hardening. Newest at the top.

| Date | Weak spot | Risk / impact | Plan to fix |
|------|-----------|---------------|-------------|
| 2026-11-03 | Model is trained and tested on PaySim, a synthetic dataset. | Interviewer: "Synthetic data was generated by a simulator, so you learned the simulator's rules, not real fraud." The 0.997 PR-AUC may not carry over to real traffic. | Answer: agreed, so I treat it as a pipeline and engineering exercise, not a claim about real fraud accuracy. I removed leaky features, used a time-based split, and chose the threshold on separate data. Next: test on a second dataset if available, monitor score drift, and retrain on real labels in production. |
| 2026-11-03 | `drains_account` and `amount_ratio` rely on PaySim fraud emptying the sender's account. | Real fraudsters may not behave this way, so these top features could be weak or easy to evade. | Review feature importance on any new data. Add features that don't depend on this one pattern, such as velocity per account. |
| 2026-11-03 | Fraud rate differs a lot between windows (train 0.24%, test 3.67% in the baseline split) and the test window has only 1,600 fraud cases. | Metrics may be unstable, and precision depends heavily on the fraud rate. | Report precision and recall with counts, try other time windows, and add confidence intervals. |
| 2026-11-03 | Only one model type (XGBoost), default-style hyperparameters, no tuning or calibration. | Scores may not be well-calibrated probabilities, so the threshold could shift on new data. | Check calibration, compare with a simple baseline such as logistic regression, and tune with the validation window only. |
| 2026-11-03 | No lock file or vulnerability scan for the Python dependencies in `ml/.venv`. | Unpinned installs can change between machines, and known CVEs go unnoticed. | Create a pinned `requirements.txt` and run a dependency scan. |
